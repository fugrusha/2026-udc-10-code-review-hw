# Пайплайн рев'ю

## Що робить `pipeline/ai-review.yml`

1. **Тригер — `pull_request` на `main`, ніколи не `pull_request_target`.** Для
   `pull_request` GitHub завжди виконує визначення воркфлоу з **базової** гілки,
   навіть якщо сам PR змінює цей `.yml`-файл. PR не може підмінити собою власний
   пайплайн і видати собі більше прав чи доступ до секретів. (У цьому репо файл
   додатково лежить у `pipeline/`, а не `.github/workflows/`, тож він узагалі не
   запускається тут — його копіюють у `.github/workflows/` вже у форку, хто
   хоче прогнати по-справжньому, це Task E.)
2. **Детерміновані перевірки — job `tests`, обов'язковий check.** `cd app && npm
   test`. Без секретів, запускається для кожного PR, включно з форками — це
   просто наявний тестовий набір, шкоди секретам нема, бо їх тут і не видно.
3. **AI-рев'ю — job `ai-review`, `needs: tests`, дорадчий коментар.** Читає
   `docs/review-standard.md` як правила, диф PR (обмежений 60 000 символів —
   захист від навмисно величезного дифу) і опис PR через `gh pr view`, формує
   системний промпт, що явно позначає весь текст із PR як **дані для оцінки, не
   інструкції** (той самий принцип, що й розділ «Недовірений вміст» стандарту),
   викликає Anthropic Messages API (`claude-sonnet-5-5`, `max_tokens: 2000`) і
   пише єдиний коментар у PR через `gh pr comment`, явно позначений як
   «дорадчо, не обов'язкова перевірка».
4. **Злиття завжди затверджує людина.** AI-коментар — це вхід для рев'юера-
   людини, не статус-перевірка; він нічого не блокує і нічого не схвалює сам.

## Права і секрети

- Верхній рівень: `permissions: contents: read` — мінімум, потрібний для
  checkout.
- `tests`: той самий мінімум (`contents: read`), секрети не передаються взагалі.
- `ai-review`: додає лише `pull-requests: write` — рівно стільки, щоб написати
  коментар; нема `contents: write`, нема `issues: write`, нема доступу до інших
  репозиторіїв чи пакетів.
- `GITHUB_TOKEN` (`${{ github.token }}`) — автоматичний токен на один прогін,
  не збережений секрет; використовується лише для `gh pr comment`.
- `ANTHROPIC_API_KEY` — єдиний справжній секрет. Job `ai-review` має
  `if: ${{ !github.event.pull_request.head.repo.fork }}`: для PR із форку цей
  job узагалі не запускається, тож секрет туди не потрапляє ні за яких умов.
  Форк отримує лише `tests` — без жодного секрета.

## Модель загроз

| Що може зробити PR зі шкідливим вмістом | Що обмежує шкоду у вашому пайплайні |
|---|---|
| Текст у описі PR, коментарях коду чи навіть фальшиве системне повідомлення намагається переконати AI-рев'юера схвалити зміну, промовчати про дефект чи «пропустити цю перевірку» | Системний промпт явно каже: весь текст із PR — дані, не інструкції. Навіть якщо модель і «послухається», її вивід — лише дорадчий коментар, ніколи обов'язкова перевірка; злиття все одно потребує людини |
| PR із форку намагається прочитати `ANTHROPIC_API_KEY` чи `GITHUB_TOKEN`, виконавши власний код у job, де є секрети | `ai-review` ніколи не виконує і не `eval`-ить вміст дифу — лише надсилає його як текст через HTTPS. А для форків цей job узагалі пропускається (`if`), тож секрет недосяжний незалежно від того, що саме намагається зробити PR |
| Навмисно величезний диф чи опис — спроба роздути вартість виклику API або витрат часу | Диф обрізається до 60 000 символів перед відправкою, відповідь обмежена `max_tokens: 2000`, і на job діє стандартний таймаут GitHub Actions |
| PR намагається змінити сам `ai-review.yml`, щоб видати собі більше прав чи обійти обмеження | `pull_request` завжди бере визначення воркфлоу з базової гілки, не з PR — зміни у форку на поточний прогін не впливають. У цьому репо файл додатково лежить поза `.github/workflows/`, тож не виконується зовсім |
| AI-коментар намагаються використати як канал, щоб «попросити» щось змінити в репо напряму | Токен job-а має лише `pull-requests: write`; у нього нема `contents: write`, тож жодна відповідь моделі фізично не може змінити вміст репозиторію |

## Що лишається на людину

Обов'язкова перевірка — лише тести (`job: tests`). AI-коментар — додатковий вхід
для людини-рев'юера, не вирок: вона вирішує, довіряти йому чи ні (як і в Task B
показано, де саме рев'юеру варто, а де не варто довіряти без перевірки), і саме
вона натискає «Merge». Для PR із форку AI-рев'ю взагалі не запускається — якщо
супроводжуючий хоче його для форку, запускає вручну поза цим пайплайном.
